Every node in this pool bills at pay-as-you-go rates. The pool has not dropped below 20 nodes in six months, so 20 of the 24 nodes are effectively permanent capacity being rented by the hour.

Buy a 1-year savings plan for the stable floor
# No change to the node pool itself. The saving is a purchase,
# not a redeploy - capacity keeps running while the rate changes.

resource "azurerm_billing_savings_plan" "compute_1yr" {
  scope         = "/subscriptions/${var.subscription_id}"
  term          = "P1Y"
  billing_plan  = "Monthly"
  # cover the 20-node floor only, leave the burst on demand
  commitment    = { amount = 11000, currency = "USD", grain = "Monthly" }
}

How the number is worked out

  • 20 nodes never released in 6 months = the committed floor
  • 20 / 24 nodes x $19,840 = $16,533 of the bill is stable capacity
  • Azure 1-year compute savings plan on D-series = about 34% off pay-as-you-go
  • $16,533 x 0.34 = $5,621, rounded down to $5,550 to allow for rate drift

What could go wrong

A savings plan is a one-year financial commitment. If the pool is retired early the commitment still bills. Covering only the 20-node floor keeps the burst capacity flexible.

Effort

One purchase, no deployment, no downtime.

Spot capacity for checkpointed jobs, and a true zero floor
resource "google_container_node_pool" "ml_training" {
  name    = "ml-training-a100-pool"
  cluster = google_container_cluster.ml.id

  autoscaling {
    min_node_count = 0      # idle days cost nothing
    max_node_count = 8
  }

  node_config {
    machine_type = "a2-highgpu-8g"
    spot         = true     # about 60-70% off, can be reclaimed
    guest_accelerator {
      type  = "nvidia-tesla-a100"
      count = 8
    }
    taint {
      key    = "cloud.google.com/gke-spot"
      value  = "true"
      effect = "NO_SCHEDULE"
    }
  }
}

# Jobs that cannot tolerate preemption opt out by tolerating
# the taint only when they checkpoint:
#   tolerations:
#     - key: cloud.google.com/gke-spot
#       operator: Equal
#       value: "true"
#       effect: NoSchedule

How the number is worked out

  • Pool ran 19 of 31 days; 12 idle days still billed the 2-node floor
  • Floor waste: 2/8 nodes x 12/31 days x $17,220 = $1,666
  • Active spend on the 19 running days = $15,554
  • 94% of runs are checkpointed and can move to spot
  • $15,554 x 0.94 x 0.45 average spot discount = $6,579
  • $1,666 + $6,579 = $8,245, rounded to $8,270 against current spot rates

What could go wrong

Spot nodes can be reclaimed with 30 seconds notice. Only jobs that checkpoint should tolerate the taint. The 6% of runs that do not checkpoint stay on an on-demand pool.

Effort

One Terraform apply plus a toleration added to the training job template. Roughly half a day.

▸bq-analytics-warehouseBigQuery, on-demand query pricing GCP Data Platform $7,340 +3.9% $2,190
Saves $2,190 a monthHigh confidence

Queries are billed per terabyte scanned. Volume has sat between 1,150 and 1,220 TiB for four consecutive months, which is stable enough to commit to slots instead. Two scheduled queries also scan full tables where a partition filter would do.

The pattern driving the scans
-- Scheduled daily, scans the full events table every run
SELECT user_id, event_type, COUNT(*) AS n
FROM `analytics.events`
WHERE event_type IN ('signup','purchase')
GROUP BY 1, 2;

-- events is 41 TB, partitioned on event_date, but the query
-- has no partition filter, so every run scans all of it.
Filter the partition, then commit to slots
-- 1. Add the partition filter (daily job only needs one day)
SELECT user_id, event_type, COUNT(*) AS n
FROM `analytics.events`
WHERE event_date = CURRENT_DATE() - 1
  AND event_type IN ('signup','purchase')
GROUP BY 1, 2;

-- 2. Enforce it so this cannot regress
ALTER TABLE `analytics.events`
SET OPTIONS (require_partition_filter = TRUE);

-- 3. Then buy a baseline slot commitment for the steady volume:
--    bq mk --capacity_commitment --plan=ANNUAL --slots=500

How the number is worked out

  • Two scheduled queries scan 41 TB daily where 0.4 TB would do
  • Wasted scan: 2 x 40.6 TB x 31 days = 2,517 TB, at $6.25/TiB = $735 (already reflected below)
  • Remaining steady volume after the fix = about 1,060 TiB
  • On-demand: 1,060 x $6.25 = $6,625
  • 500 annual slots = $5,170/month flat, and covers the measured peak
  • $735 partition saving + $1,455 slot saving = $2,190

What could go wrong

Slot commitments cap concurrency. Peak slot usage measured over 90 days was 430, so 500 leaves headroom. require_partition_filter will break any query that omits the filter, which is the point, but it needs an announcement first.

Effort

Two query edits, one table option, one purchase. About two hours plus a notice period.

▸openai-embeddings-prodManaged model endpoint, 41M tokens AZURE ML Platform $6,510 +18.7% $1,300
Saves $1,300 a monthMedium confidence

Embeddings are recomputed on every document ingest, including for documents whose text has not changed. A content hash check would skip most of them. Nothing is batched, so everything pays the real-time rate.

ingest/embed.py (current)
def ingest(doc):
    # Every ingest embeds, whether or not the text changed
    vector = client.embeddings.create(
        model="text-embedding-3-large",
        input=doc.text,
    ).data[0].embedding
    store.upsert(doc.id, vector)
Skip unchanged text, batch the rest
import hashlib

def ingest(doc):
    digest = hashlib.sha256(doc.text.encode()).hexdigest()
    if store.get_digest(doc.id) == digest:
        return                      # text unchanged, vector still valid
    pending.append((doc.id, doc.text, digest))

def flush(pending):
    # One call per 512 documents instead of one per document
    vectors = client.embeddings.create(
        model="text-embedding-3-large",
        input=[text for _, text, _ in pending],
    ).data
    for (doc_id, _, digest), v in zip(pending, vectors):
        store.upsert(doc_id, v.embedding, digest=digest)

How the number is worked out

  • 41M tokens billed this month
  • Ingest logs: 62% of documents re-ingested with byte-identical text
  • Hash check removes 25.4M tokens, but re-embedding after model upgrades still needed
  • Conservative estimate: 20% token reduction = $1,302
  • Batching adds no direct token saving, it reduces per-call overhead only

What could go wrong

The digest must be invalidated when the embedding model version changes, or stale vectors persist silently. Store the model name alongside the digest.

Effort

A small code change plus a schema column. Half a day, and it needs a backfill decision.
